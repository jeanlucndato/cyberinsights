🐝 Hive — Observer.
Analyser. Comprendre.

Hive transforme les interactions avec des services leurres en un parcours d’investigation consultable en temps réel. Quatre capteurs Go, adaptés à leurs protocoles, alimentent une console React et TypeScript. Les observations peuvent être exportées au format STIX 2.1 et en suggestions de règles réseau à valider.

Prise en main

Lancer Hive en laboratoire

Deux modes sont documentés : le lancement local pour explorer et développer, ou Docker Compose pour démarrer un profil conteneurisé. Dans les deux cas, les ports publiés restent liés à la boucle locale par défaut.

1. Préparer l’environnement

Cloner le dépôt Hive, puis installer Go 1.26.4 ou supérieur et Node.js 20.19+ ou 22.12+ avec npm. Le dépôt du portfolio affiché ici contient la page de présentation, pas le code source ni le lanceur Hive.

Dépôt GitHub de ce portfolioTous mes dépôts

Le code source Hive est distinct de ce site portfolio. L’URL du dépôt Hive n’apparaît pas dans les fichiers fournis ; le lien ci-dessus ouvre le dépôt vérifié de ce portfolio.

2. Démarrer en mode local

Depuis la racine du dépôt Hive, exécuter le lanceur. Il installe les dépendances du tableau de bord si nécessaire puis démarre le backend Go et le serveur de développement Vite. Garder le terminal ouvert ; Ctrl+C arrête les services.

./run-local.sh

Ouvrir ensuite http://127.0.0.1:5173, puis choisir Site leurre dans la barre latérale.

3. Générer des événements d’essai

Essayer une requête HTTP puis une session SSH. Le SSH accepte un mot de passe quelconque, mais ne l’enregistre pas et ne lance aucune commande sur la machine.

curl http://127.0.0.1:8080/wp-login.php
ssh -p 2222 root@127.0.0.1

Pour MySQL et Redis, si les clients sont installés : mysql --protocol=TCP -h 127.0.0.1 -P 3306 -u demo et redis-cli -h 127.0.0.1 -p 6379 PING.

4. Variante Docker Compose

Configurer un jeton API avant de publier les conteneurs. Exemple PowerShell :

$env:HIVE_API_TOKEN = "remplacer-par-un-jeton-aleatoire"
docker compose up --build

Le tableau de bord est disponible sur http://127.0.0.1:5173. Saisir le jeton quand l’interface le demande. Les données sont conservées dans le volume hive-data.

Architecture & circulation des événements

De l’interaction leurre à l’investigation

Chaque capteur traduit les interactions de son protocole dans un flux d’événements commun. La diffusion à files bornées évite qu’un client lent ne bloque les capteurs ; le journal local conserve un historique consultable.

Capteurs adaptés aux protocoles

SSH : collecte le nom de connexion et les commandes shell ou exec, puis répond avec un faux shell ; le mot de passe est écarté et aucune commande ne s’exécute sur l’hôte. HTTP : relève méthode, chemin, agent utilisateur et corps de requête borné ; le site leurre enregistre aussi les clics et les noms des champs du formulaire, jamais leurs valeurs. MySQL : extrait le nom d’utilisateur d’un paquet de connexion borné, refuse l’accès et ne conserve pas la réponse d’authentification. Redis : interprète les commandes inline et RESP avec des réponses minimales ; les valeurs AUTH et les affectations courantes de secrets sont masquées.

Pipeline d’événements commun

À la publication, le bus attribue un identifiant d’événement et de capteur, enrichit l’observation avec des tags MITRE ATT&CK heuristiques, la conserve dans une fenêtre mémoire, l’ajoute au journal puis la distribue aux abonnés via des files bornées. Un client lent ne bloque donc pas les capteurs ; les pertes de livraison et erreurs du journal sont mesurées.

Console d’analyse

Au chargement et lors d’une recherche, le client interroge l’API pour retrouver les événements récents ou parcourir le journal. En parallèle, un WebSocket reconnecté avec temporisation transmet les nouvelles observations. L’interface fusionne ces deux usages, filtre par service, ouvre le détail d’un événement, affiche l’état de livraison et de stockage et exporte les résultats filtrés en CSV.

Indicateurs à valider

Un abonné de renseignement déduplique les adresses IP sources valides et produit des indicateurs STIX 2.1 ainsi qu’un fichier de commandes pare-feu suggérées. Ces artefacts sont des pistes d’enquête : une adresse observée n’est pas une preuve d’intention malveillante et aucune règle n’est appliquée automatiquement.

Sous le capot

Le trajet d’un événement, étape par étape

Ce parcours relie l’entrée réseau à une investigation exploitable, tout en gardant le traitement des capteurs indépendant des consommateurs en aval.

1. Interaction avec le leurre

Un client se connecte à l’un des ports dédiés. Le capteur applique les limites propres à son protocole : taille des paquets et corps bornés, analyse du format, puis réponse de leurre adaptée.

2. Normalisation

Le capteur publie une observation typée avec l’adresse source, le service, le type d’événement, l’horodatage et une charge utile assainie. Les quatre protocoles alimentent ainsi un modèle commun.

3. Enrichissement & distribution

Le bus complète l’événement, applique des correspondances ATT&CK heuristiques, le retient en mémoire et le transmet aux abonnés via des files de capacité bornée afin d’isoler les capteurs des consommateurs lents.

4. Journal consultable

Les événements sont ajoutés à un journal JSONL local qui tourne à 64 Mio et garde une sauvegarde. La recherche parcourt le fichier actif et le fichier rotatif ; une rétention en jours peut être configurée. C’est simple à inspecter et adapté aux labs, mais moins efficace qu’une base indexée pour de gros volumes.

5. Investigation & export

L’API REST sert l’état de santé, les métriques, les événements récents et la recherche paginée. Le WebSocket livre les nouveaux événements ; le navigateur peut se reconnecter et l’analyste exporte les résultats filtrés en CSV. Les observations IP peuvent alimenter les exports STIX et les suggestions à valider.

Décisions de conception

Le débit ne doit pas compromettre la maîtrise

Les choix de Hive privilégient un comportement prévisible et observable dans un environnement de laboratoire.

  • Files bornées : un abonné lent ne bloque pas le traitement réseau ; les livraisons abandonnées restent visibles dans les métriques.
  • Historique séparé du temps réel : la recherche relit le journal tandis que le WebSocket transporte les nouveaux événements. Après une coupure, le navigateur se reconnecte et l’historique reste interrogeable.
  • API protégée en exposition : les services démarrent sur la boucle locale. Une API liée à une adresse non locale exige un jeton bearer et des origines autorisées.
  • Sorties opérateur : STIX et commandes pare-feu documentent des indicateurs ; la décision de blocage est volontairement laissée à un humain.

Interfaces utiles

GET /api/health — santé et identifiant du capteur

GET /api/events — derniers événements en mémoire

GET /api/search — recherche paginée dans le journal

GET /api/metrics — abonnés, pertes et erreurs d’écriture

GET /ws/events — diffusion temps réel

Les pages API et WebSocket nécessitent un jeton bearer lorsque l’API écoute au-delà de la boucle locale.

Déploiement maîtrisé

Des leurres dans un laboratoire isolé

Hive est conçu pour l’observation contrôlée et l’expérimentation, pas comme serveur de production ou SOC clé en main. Le shell SSH n’exécute aucune commande sur l’hôte. Les émulations sont limitées et les tags ATT&CK restent des pistes heuristiques, pas une preuve d’activité malveillante.

  • Tous les services écoutent sur 127.0.0.1.
  • Une écoute API hors boucle locale exige un jeton bearer ; gardez cette API privée.
  • La collecte reste minimisée selon le service, mais des corps de requête HTTP ou d’autres données envoyées par un visiteur peuvent contenir des informations sensibles. La rédaction est au mieux des possibilités et ne garantit pas une anonymisation complète. Définissez rétention et contrôle d’accès avant toute collecte externe.
  • Examinez les suggestions pare-feu manuellement. N’exécutez jamais le fichier généré directement dans un shell.
  • Avant toute exposition, utilisez un hôte dédié et isolé, sans identifiants de production.

Périmètre & évolutions

Un projet d’expérimentation

Hive utilise des fichiers JSONL rotatifs à taille limitée plutôt qu’une base indexée. Les émulations restent ciblées, les corrélations ATT&CK sont heuristiques et l’enrichissement GeoIP n’est pas inclus. Pour traiter davantage de données, les pistes d’évolution sont un stockage indexé, une administration plus complète des capteurs et un enrichissement configurable en renseignement sur les menaces.

Les captures présentent le tableau de bord et le site leurre. Le README décrit aussi le lancement du backend et le parcours SSH simulé.
